# 16. Learning and personal development plan

**Purpose:** turn the project into demonstrable learning rather than only a feature list. This is a plan, not a claim that every skill or milestone was achieved.

## Learning areas

| Area | Practical outcome |
|---|---|
| Planetary GIS | Explain why Mars coordinates cannot be treated as Earth WGS84 by default |
| Data engineering | Acquire one original product, retain metadata and reproduce a derivative |
| Scientific communication | Distinguish detection, interpretation and assumption |
| Product scope | Connect a narrow user workflow to challenge requirements |
| Frontend integration | Share consistent map, route and scene state |
| Testing | Explain what a test demonstrates and what it cannot validate |
| Collaboration | Assign bounded work, communicate blockers and review contributions |
| Public communication | Present the working product and its limits in English |

## Historical preparation plan

- Week 1, 2026-10-24–2026-10-28: challenge context, Mars science and literature discovery.
- Week 2, 2026-10-29–2026-11-04: data access, metadata and processing concepts.
- Week 3, 2026-11-05–2026-11-13: scope, responsibilities and narrative preparation.

Implementation timing remains subject to official event guidance [S03].

## Learn by doing

For each contributor, choose one artifact they can explain without relying on the assistant: a source card, coordinate check, map interaction, reproducible bug, lightweight asset or source-backed scientific explanation.

Recommended references: mission pages [S60–S71], USGS mapping guidance [S50], source archives [S14–S16, S58–S59] and EVA-planning literature [S27–S33].

## Personal working rules

Prefer a small complete task, ask for help when blocked, avoid taking over every role, preserve rest and make uncertainty visible. Use generative AI to assist understanding, not to replace checking sources or learning how the implementation works.

## Evidence of learning

Record an independently explained concept, a reproducible artifact, a reviewed contribution and a lesson from failure. Do not equate generated code volume, features proposed or hours worked with learning outcomes.

After the event, write a short retrospective: what was learned, what remains unclear, what should be removed and the next focused experiment.

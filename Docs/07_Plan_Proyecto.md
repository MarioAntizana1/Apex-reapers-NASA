# 07. Project execution plan

**Status:** planning reference, not a record of completed milestones. The project records use a 2026-11-14–2026-11-15 event window; official schedules and local deadlines require confirmation [S01–S03].

## Work packages

| Package | Deliverable | Main dependency |
|---|---|---|
| Research | Bibliography, data catalog and known gaps | Original sources |
| Product | Narrow user workflow and acceptance criteria | Challenge interpretation |
| Data | Checked metadata and reduced web assets | Acquisition, CRS and rights review |
| Application | Map, planning interaction and coherent state | Shared data contracts |
| Science | Source-backed explanations and POIs | Appropriate observations |
| Validation | Software results and separate science/data review | Working integration |
| Communication | Demonstration, English documentation and submission | Honest delivery status |

## Historical pre-event plan

- 2026-10-24–2026-10-28: investigate the challenge, literature and data access.
- 2026-10-29–2026-11-04: refine data catalog, responsibilities and open questions.
- 2026-11-05–2026-11-13: review official resources, scope and submission requirements.

These entries describe the planned preparation, not proof that every activity occurred.

## Event plan

| Phase | Priority | Gate |
|---|---|---|
| Opening | Confirm actual rules, data area, owner and contracts | No incompatible coordinate assumptions |
| First integration | Small valid dataset, map and core interaction | Sources and missing data visible |
| Main build | Route/planning interaction and scientific context | One coherent user flow |
| Validation | Software tests, source review and new-user checks | Critical issues fixed; gaps recorded |
| Freeze | No nonessential features; stabilize and document | Deliverable matches claims |
| Submission | Verify links, credits, disclosure and mandatory fields | Human confirms actual submission |

Protect time for review, rest and publication; do not spend the entire event on 3D decoration.

## Risks and contingencies

| Risk | Response |
|---|---|
| Archive or network unavailable | Use checked local assets; record observation/access dates |
| DTM unsuitable or incomplete | Restrict coverage and use clearly labelled context; never invent heights |
| Route/resource model criticized | Publish assumptions; remove unsupported safety claims |
| Missing contributor | Reassign a bounded deliverable and reduce scope |
| Slow or broken 3D | Preserve 2D; use documented fallback in [21](21_Pruebas_y_Contingencia_3D.md) |
| Scope growth | Keep only traceable core work; move extras to roadmap |
| Submission/demo fails | Prepare a recording and verify public links early |
| Rights or AI history incomplete | Disclose uncertainty; do not claim blanket ownership |

## Definition of done

A task needs an identifiable artifact, owner, applicable check and documented limitations. “Designed,” “implemented,” “tested” and “scientifically validated” are different states.

Planned KPIs include task completion, route response time, documented layer coverage, reproducible acquisition and presentation clarity. Targets in [09](09_Plan_de_Validacion.md) are not measured outcomes.

## After the event

Record what actually shipped, synchronize deployment and source, resolve asset rights, seek expert review, reproduce data in a fresh workspace and collect user feedback before expanding scope.
